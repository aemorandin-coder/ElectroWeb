# C-08 — Anti-abuso: captcha real y "Solicitar producto" solo con cuenta
Estado: HECHO
Rama: claude/C-08 — **apilada sobre `claude/C-06`** (misma API `product-requests`). Mergear C-04 → C-06 → C-08.
Decisiones de Andrés: "Solicitar producto" solo con cuenta. Captcha verificado en el servidor.

## ⚠️ Antes de desplegar
Agrega en el `.env` de **producción**: `HCAPTCHA_SECRET=<clave secreta del panel de hCaptcha>`. La pública (`NEXT_PUBLIC_HCAPTCHA_SITE_KEY`) ya está configurada: el sitio usa `c762f7c6-…`.
**Sin `HCAPTCHA_SECRET`, en producción el registro, recuperar contraseña, contacto y solicitar producto responden 503** (falla cerrado a propósito, para no quedar abiertos a bots).

## Qué cambió
- **`lib/captcha.ts` (nuevo):** `verifyCaptcha(token, ip)` consulta `api.hcaptcha.com/siteverify` con el secreto, la IP y la clave pública, con timeout de 8 s. Sin token o con token inválido → 400; sin secreto en producción → 503; sin secreto en desarrollo → se omite.
- **Verificación en el servidor** (antes el captcha solo se revisaba en el navegador y un bot llamaba directo a la API): `POST /api/auth/register`, `/api/auth/forgot-password`, `/api/contact` y `/api/product-requests`. Cada respuesta usa la forma que ya lee su formulario (`error` o `message`).
- **`POST /api/product-requests`**
  - **Solo con cuenta:** sin sesión → `401 { error: 'Inicia sesión para solicitar un producto.' }`. Antes el proxy redirigía al login, `fetch` recibía el HTML con 200 y **el formulario mostraba "¡enviado!" sin guardar nada** (comprobado en `next dev`).
  - Validación con `zod`: nombre 2–100, correo válido ≤ 200, teléfono ≤ 30, producto 2–150, descripción ≤ 2000, categoría ≤ 60, presupuesto numérico 0–10.000.000. Error → 400 con `field`.
  - **Límite:** 5 solicitudes válidas por hora por usuario (429). Los errores de validación y captcha no gastan intentos.
  - **Bug corregido:** el formulario envía `productDescription` y la API leía `description`, así que **la descripción nunca se guardaba**. Ahora se aceptan los dos nombres.
  - Siempre notifica al usuario (link `/customer`).
- **`proxy.ts`:** `/api/product-requests` pasa al handler sin redirigir (lista de APIs públicas). GET, PATCH y DELETE siguen exigiendo permisos de admin dentro del handler (C-06).
- **`env.example.txt`:** documenta las dos variables de hCaptcha y las claves de prueba oficiales.
- **`PLAN_GEMINI.md`:** tarjeta **G-18** (aviso "Inicia sesión" en el formulario, botón deshabilitado sin sesión y precarga de nombre y correo).

- **Arnés con handlers reales y la API real de hCaptcha** (claves de prueba oficiales, no las de Andrés): **15/15 PASS**.
  - `verifyCaptcha`: token de prueba válido → ok · token inventado → 400 · sin token → 400 · producción sin secreto → 503 · desarrollo sin secreto → se omite.
  - Solicitudes: invitado → 401 JSON · captcha falso → 400 sin guardar · correo inválido → 400 con `field` · texto de 500 caracteres → 400.
  - Solicitud válida → 201, con el usuario de la sesión aunque el body mande `userId: 'victima'`, la descripción guardada y el presupuesto como número.
  - Límite: la 6.ª solicitud válida en la hora → 429, con 5 guardadas (los errores previos no contaron).
  - Registro con captcha falso → 400 · recuperar contraseña sin captcha → 400 · contacto con captcha falso → 400 y con captcha válido → 201.
