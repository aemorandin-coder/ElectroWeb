# C-105 — IP real del cliente
Estado: HECHO EN CÓDIGO — **falta que Andrés ajuste el nginx del servidor** (pasos abajo)
Rama: `claude/C-105` (desde `claude/C-109`: las dos tocan `app/api/analytics/route.ts`).

## El problema
- A todos los clientes les aparecía la misma IP. Next rellena `x-forwarded-for` con la dirección del socket cuando no le llega (`node_modules/next/dist/server/base-server.js`, `??=`). Detrás de nginx esa dirección es `::1` o `127.0.0.1`: **nginx no está mandando la IP del cliente**.
- Había seis copias de `x-forwarded-for.split(',')[0]`. Ese primer valor lo escribe el propio cliente, así que:
  - **Los límites por IP eran compartidos por toda la tienda** (todos tenían la misma "IP"): 30 fallos de login en 15 minutos, venga de quien venga, bloqueaban el login por IP a todos. Igual con registro, contacto, recuperar clave, canje de gift cards y analítica.
  - Con nginx ya configurado, quien cambiara esa cabecera en cada intento **se saltaba cualquier límite**.
  - **El modo mantenimiento se saltaba** mandando `X-Forwarded-For: <IP permitida>`.
  - La firma de los términos del saldo guardaba la cadena entera (`"a, b, c"`) como IP.

## Qué cambió
- **`lib/ip.ts`** (nuevo), una sola fuente:
  1. `x-real-ip`, que nginx pisa con `$remote_addr`.
  2. Si no, `x-forwarded-for` **de derecha a izquierda** (el último valor lo agrega nginx).
  - Solo acepta IP públicas: descarta loopback, redes privadas, enlace local, CGNAT y `::`.
  - Normaliza `::ffff:1.2.3.4`, puertos y corchetes.
  - Sin IP válida: `null` (o "desconocida" para registros y límites), nunca `::1` como si fuera un cliente.
- La usan: `lib/rate-limit.ts` (`getClientIP`, y con ella todos los límites), `lib/audit-log.ts`, `lib/maintenance.ts` (también normaliza la lista de IP permitidas), `lib/auth.ts` (último acceso y límite del login), `app/api/analytics` y `app/api/customer/balance/terms`.
- Ya no queda ninguna lectura directa de `x-forwarded-for` ni `x-real-ip` fuera de `lib/ip.ts`.

## Cómo se verificó
- **33 pruebas de `lib/ip.ts` y del mantenimiento** (tsx):
  - nginx sin configurar (`::1`, `::ffff:127.0.0.1`) → null.
  - nginx configurado → la IP real.
  - XFF falsificado a la izquierda → gana la que agrega nginx; `x-real-ip` manda sobre un XFF falso.
  - IPv6 pública; cabeceras basura; rangos privados y sus bordes (172.15 / 172.32, 100.63).
  - Mantenimiento: un XFF falso con la IP permitida **no pasa**; la IP permitida real sí.
- **De punta a punta** con `next dev` y la tienda de ejemplo: `POST /api/analytics` guardó "desconocida" sin cabeceras, `190.202.10.5` con las de nginx y `186.14.2.9` con un XFF falso delante.
- `npx tsc --noEmit`: 0. ESLint contra `claude/C-109`: ningún archivo empeora (`lib/auth.ts` sigue con sus 14 `any` de antes).
- Efecto en la base de ejemplo: 3 eventos `prueba_c105` en `rev10_demo.analytics_events`.

## Para Andrés: nginx del servidor
Sin esto el código es seguro, pero todos seguirán apareciendo como "desconocida". Pasos en el resumen del 24/09 y aquí:
1. Ver el bloque: `sudo nginx -T 2>/dev/null | grep -n -B2 -A12 "proxy_pass"`.
2. Dentro de ese `location` (junto al `proxy_pass`):
   ```
   proxy_set_header X-Real-IP $remote_addr;
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   proxy_set_header X-Forwarded-Proto $scheme;
   ```
3. **Si el dominio pasa por Cloudflare** (`curl -sI https://<dominio> | grep -i cf-ray` devuelve algo), además hay que decirle a nginx que confíe en Cloudflare (`set_real_ip_from` con sus rangos y `real_ip_header CF-Connecting-IP`). Si no, todos aparecerían con IP de Cloudflare.
4. `sudo nginx -t && sudo systemctl reload nginx`.
