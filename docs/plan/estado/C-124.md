# C-124 · Moderación de reseñas: el 500 al aprobar

Estado: HECHO (2026-09-29, rama `claude/C-124`, sale de `main` en 3267cfd). **Lleva cambio de base:** 2 columnas nuevas en `reviews`.

## Lo que vio Andrés en producción
Admin → Reseñas → aprobar la reseña de Luis Morandin: `PATCH /api/reviews` respondía 500 y el toast decía "Error al aprobar reseña".

## Causa (demostrada)
- El panel mandaba `{ id, isApproved: true, isPublished: true }` y la API copiaba `isPublished` al `UPDATE`.
- **`reviews` no tiene la columna `isPublished`.** Prisma lanza `PrismaClientValidationError: Unknown argument isPublished` (reproducido con el cliente de Prisma contra `rev10_demo`), y el `catch` lo convertía en un 500 sin detalle.
- No era la URL (la API siempre esperó el `id` en el cuerpo), ni un enum en español, ni la sesión: la cookie de NextAuth viaja sola y el permiso se revisaba bien.
- El mismo campo inexistente rompía más cosas:
  - En el panel, la pestaña "Aprobadas" y el estado "Publicada" dependían de `isPublished`: **nunca coincidían con nada**.
  - "Rechazar" dejaba la reseña igual que una pendiente: no existía el estado "rechazada".
  - En "Mis reseñas" del cliente, ninguna salía como "Publicada".
- **Transacción para el promedio:** no hace falta. Las estrellas no se guardan en `products`; `getReviewSummary` las calcula de las reseñas aprobadas en cada lectura. Aprobar es un solo `UPDATE`.

## Qué se hizo
- **Base:** `reviews.rejectedAt` y `reviews.rejectionReason` (solo `ADD COLUMN`, nulas).
  - Pendiente = sin aprobar y sin `rejectedAt`. La regla vive en `lib/review-status.ts` y la usan la API y los dos paneles.
- **`PATCH /api/reviews`:**
  - Moderación: `{ id, action: 'approve' | 'reject', reason? }`. Acepta también `{ id, isApproved }` (pestañas abiertas antes del deploy) e **ignora `isPublished` y cualquier otro campo**.
  - El dueño edita nota y comentario. Al editar, la reseña vuelve a pendiente (también si estaba rechazada).
  - Errores siempre como `{ success: false, error }` con su código (400, 403, 404, 500). En un 500, el admin recibe además `detail` y `prismaCode`; el cliente no ve nombres de tablas.
  - El log del servidor registra `id`, acción, código de Prisma y el error completo.
  - El correo y la notificación de "reseña publicada" salen con `after()`, después de responder: un SMTP lento ya no demora ni tumba la aprobación.
  - Si cambia lo publicado, se regenera la tienda (`revalidateStorefront`), porque las tarjetas del home muestran estrellas.
- **`DELETE`:** mismo permiso que el resto (`hasPermission`), mismos errores.
- **Contadores de pendientes** (menú del admin, `/api/stats` y el resumen de Telegram): ya no cuentan las rechazadas.
- **Panel Admin → Reseñas** (rehecho):
  - Pestañas Pendientes, Publicadas, Rechazadas y Todas, con conteo. Abre en Pendientes.
  - **Se ve qué producto se reseñó** (antes no salía), con enlace a la ficha.
  - Acciones: Publicar, Rechazar o Retirar (si ya estaba publicada), con motivo opcional que el cliente ve, y Eliminar.
  - El toast muestra el error real del servidor.
  - La fila se actualiza sin recargar la lista.
  - En el teléfono, tarjetas con los botones a la vista; en escritorio, tabla.
- **Mis reseñas (cliente):** "Publicada", "Pendiente" o "No publicada" con el motivo.
  - Es carril Gemini; se tocó por el pedido de Andrés sobre el panel del cliente (punto 4 del 29/09).

Inventario (CHATGPT.md §4): se conservan todas las acciones y datos del panel. Se quitaron la foto del usuario, el título y "Compra verificada" porque la API nunca los mandaba (siempre salían vacíos).
