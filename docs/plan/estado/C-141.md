# C-141 · Equipo, roles y verificación en dos pasos del panel

Estado: EN CURSO — rama `claude/C-141` con un commit a medias. **No mergear así:** los permisos ya exigen los dos pasos, pero todavía no existe la pantalla para configurarlos, y ningún admin podría usar el panel.

## Decisiones de Andrés (30/09, noche)
- **Dos pasos:** app de códigos (Google Authenticator o Authy), obligatoria para todo el panel, con 10 códigos de respaldo.
- **Roles:**
  - **Super admin** (Andrés, dueño): todo.
  - **Administrador:** todo el día a día, menos la configuración sensible y el equipo.
  - Soporte, ventas o contenido: no por ahora.
  - *Interpretación de Claude* (Andrés marcó solo "Administrador"): él sigue como super admin y el equipo entra como Administrador. Confirmarlo si hay dudas.
- **Admins nuevos:** por invitación al correo. Cada uno crea su contraseña y sus dos pasos; el dueño nunca la conoce.
- **Orden:** C-141 antes que C-139 (Puntos ES).

## Lo que encontró la revisión de roles
- Solo había dos roles efectivos, Admin y Super admin, y los dos con acceso a todo. `hasPermission` le daba todo a los dos.
- Soporte no entra al panel: `isAdmin` es solo ADMIN o SUPER_ADMIN.
- Los permisos por persona no se guardan en ninguna parte: `authorize` devuelve siempre `permissions: []`.
- No hay pantalla para crear admins. Solo `scripts/create-master-admin.ts`, que siempre crea un super admin.
- **Herramientas viejas para borrar:**
  - `scripts/update-admin-role.js` convierte a *todos* los admin en super admin (y tiene emojis).
  - `app/api/admin/promote-super-admin` está apagada sin `SUPER_ADMIN_PROMOTION_KEY`.
- En `lib/auth.ts` había una "regla de sesión única del super admin" que borraba filas de `Session` (el adaptador de NextAuth, sin uso con JWT). Código muerto: C-140 la reemplaza de verdad. Ya se quitó.

## Hecho (en el commit a medias)
- **Esquema:** modelo `SegundoFactor` (`segundo_factor`) y relación `User.segundoFactor`.
  ```sql
  CREATE TABLE "segundo_factor" (
      "userId" TEXT NOT NULL, "secreto" TEXT NOT NULL, "activadoAt" TIMESTAMP(3),
      "ultimoPaso" INTEGER NOT NULL DEFAULT 0, "codigosRespaldo" TEXT[],
      "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP, "updatedAt" TIMESTAMP(3) NOT NULL,
      CONSTRAINT "segundo_factor_pkey" PRIMARY KEY ("userId")
  );
  ALTER TABLE "segundo_factor" ADD CONSTRAINT "segundo_factor_userId_fkey" FOREIGN KEY ("userId") REFERENCES "users"("id") ON DELETE CASCADE ON UPDATE CASCADE;
  ```
  Todavía no se aplicó en `rev10_demo`. Generarlo con `prisma migrate diff --from-schema-datamodel <schema de main> --to-schema-datamodel prisma/schema.prisma --script` y aplicarlo con `SET search_path TO rev10_demo;` delante.
- **`lib/dos-pasos.ts`:**
  - TOTP (RFC 6238, SHA-1, 30 s, 6 dígitos) con `crypto`, sin dependencias nuevas.
  - **Verificado con los 6 vectores del apéndice B del RFC: 6/6.** El secreto de prueba `GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ` da 287082 en t=59.
  - El secreto se guarda cifrado (AES-256-GCM, clave derivada de `NEXTAUTH_SECRET`, como el token de Telegram).
  - Tolera ±30 s y no acepta dos veces el mismo intervalo (`ultimoPaso`).
  - 10 códigos de respaldo `XXXX-XXXX`, guardados como HMAC y de un solo uso; se gastan con un `updateMany` condicionado.
  - El QR se arma como SVG en el servidor con `qrcode-generator` (ya es dependencia). El secreto nunca pasa por servicios externos como `api.qrserver.com`, que usan los certificados.
  - Funciones: `estadoDosPasos`, `iniciarDosPasos` (QR, clave legible, `otpauth://`), `activarDosPasos`, `verificarCodigo`, `regenerarRespaldo`, `reiniciarDosPasos`.
- **`lib/auth.ts`:**
  - Credencial nueva `codigo`.
  - Admin con los dos pasos activos: sin código, error `CODIGO_REQUERIDO` (no cuenta como fallo); código malo, `CODIGO_INVALIDO` (cuenta como fallo, con el mismo límite de intentos de C-80 y queda en la bitácora).
  - `registrarAcierto` se movió para después del código.
  - `dosPasos` va en el usuario, el JWT y la sesión. El `update()` de NextAuth lo refresca desde la base.
- **`types/next-auth.d.ts`:** `dosPasos` en Session, User y JWT.
- **`lib/auth-helpers.ts`:**
  - `hasPermission`: ADMIN y SUPER_ADMIN **sin permisos hasta `dosPasos === true`**.
  - ADMIN tiene todo menos `SOLO_DUENO = ['MANAGE_SETTINGS', 'MANAGE_TEAM']`. `MANAGE_SETTINGS` protege Configuración, Métodos de pago, correo, Telegram y avisos, y documentos legales.
  - Nueva `esAdminVerificado(session)`.
- **14 revisiones que miraban solo el rol** (se saltaban los dos pasos) ahora usan `esAdminVerificado`:
  - `api/admin/sades/search`, `api/admin/sades/health`, `api/admin/discount-requests` (2).
  - `api/customer/chat/[conversationId]` y su `message`.
  - `api/digital-codes` (3), `api/gift-cards` (2), `api/orders/[id]/digital` (2).
  - `api/uploads/[...path]` (documentos privados).
- `npx tsc --noEmit` pasa. **No hay pruebas en ejecución todavía** (solo las del RFC).

## Falta, en este orden
1. **Advertencia del build** "Dynamic filesystem access" (captura de Andrés del 30/09): en `app/api/uploads/[...path]/route.ts`, poner `/*turbopackIgnore: true*/` en `readFile` y `existsSync`. La ruta ya se valida con `isInside`. Comprobar con `npm run build` que la advertencia desaparece.
2. **API `/api/admin/dos-pasos`** (solo admin, **sin** exigir `dosPasos`: es para configurarlos):
   - GET: el estado.
   - POST `iniciar`: QR, clave y `otpauth://`.
   - POST `activar {codigo}`: activa, devuelve los 10 códigos **una sola vez**, **cierra las demás sesiones** con `cerrarLasDemas` (si alguien entró con la contraseña antes de la activación, queda fuera) y el navegador llama a `update()`.
   - POST `regenerar {codigo}`.
3. **Página `/admin/seguridad`** (todos los admin):
   1. Instala la app.
   2. Escanea el QR; en el teléfono, botón "Abrir en la app de códigos" (`otpauth://`); o copia la clave.
   3. Escribe el código.
   4. Guarda los 10 códigos: copiar, descargar `.txt` y "Ya los guardé".
   - Estado y "Generar códigos nuevos". Sin "desactivar": son obligatorios; solo se reinician desde Equipo o con el guion.
4. **`proxy.ts`:**
   - Páginas `/admin/*` con token de admin y `dosPasos !== true` → redirigir a `/admin/seguridad`. Excepciones: esa misma página y `/admin/login`.
   - `/api/admin/*` → 403 JSON salvo `/api/admin/dos-pasos`.
   - `sidebar-counts`: admin sin dos pasos → **403** (no 401: el layout cierra la sesión con 401, C-140).
5. **Login (`app/login/LoginCliente.tsx`):**
   - `CODIGO_REQUERIDO` → segundo paso con un campo para el código (`inputMode="numeric"`, `autoComplete="one-time-code"`) y "Usar un código de respaldo". Se vuelve a llamar a `signIn` con el mismo correo y contraseña más `codigo`.
   - `CODIGO_INVALIDO` → "El código no es correcto".
6. **Layout del admin:**
   - Usar `hasPermission` de `lib/auth-helpers`; hoy tiene su propia copia que le da todo al ADMIN.
   - Agregar "Equipo" (`MANAGE_TEAM`) y "Mi seguridad".
   - En `/admin/seguridad` sin dos pasos: sin menú ni contadores.
7. **Equipo** (`/admin/equipo` + `/api/admin/equipo`, con `MANAGE_TEAM`, solo el super admin):
   - Lista: nombre, correo, rol, dos pasos (activos o pendientes), última entrada (`user_sessions`) y estado (activo, sin acceso, invitación pendiente).
   - **Invitar** (correo, nombre, rol Administrador o Super admin):
     - Crea el usuario sin contraseña.
     - Crea un `PasswordResetToken` de **24 h**.
     - Manda un correo de invitación con el enlace a `/recuperar-contrasena/<token>`. Esa página, con `?invitacion=1`, debe decir "Crea tu contraseña".
     - `reset-password` debe poner `emailVerified` si estaba vacío.
     - Si el correo ya existe (cliente o equipo) → error, sin convertir cuentas.
   - **Acciones** (nunca sobre uno mismo; siempre queda al menos un super admin activo):
     - Cambiar el rol.
     - Quitar el acceso (`accountStatus = SUSPENDED` y cerrar sesiones; `sesionValida` ya lo corta). Devolver el acceso.
     - Reiniciar los dos pasos (`reiniciarDosPasos` y cerrar sesiones).
     - Reenviar la invitación. Cerrar sus sesiones.
     - Todo queda en la bitácora (`registrarAccionAdmin`).
   - `settings/_components/SystemSection.tsx` (lista de admins de solo lectura) → enlace a Equipo.
8. **Guion de emergencia** `scripts/reset-dos-pasos.ts <correo>`, para correr en el servidor si Andrés pierde el teléfono y los códigos.
9. **Borrar** `scripts/update-admin-role.js` y `app/api/admin/promote-super-admin/`.
10. **Pruebas** (`rev10_demo`, login real por HTTP como en C-140):
    - Vectores del RFC. Entrar con código; el mismo código dos veces → no; código de respaldo de un solo uso; código malo cuenta como fallo.
    - Admin sin dos pasos: redirigido, 403 en las APIs de permisos y sí puede configurarlos.
    - Activar cierra las demás sesiones.
    - Administrador: sin Configuración ni Equipo (menú y API) y con todo lo demás.
    - Equipo: invitar, crear la contraseña, primer ingreso con configuración obligatoria, quitar y devolver el acceso, reiniciar, el último super admin protegido.
    - Navegador a 360 y 1440 px.
11. Estado HECHO, `SIGUIENTE.md` con el SQL y las pruebas, merge y push (regla 2 de `CLAUDE.md`).

## Riesgos para el deploy
- **Después del deploy, el panel no se puede usar hasta configurar los dos pasos** (es lo que se decidió). Andrés debe hacerlo **en cuanto termine el deploy**: mientras tanto, alguien con su contraseña podría registrar su propia app.
